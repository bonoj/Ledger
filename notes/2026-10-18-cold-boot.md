# Cold Boot — 18 October 2026

## Experiment
The human opened a new conversation with “Sanctum!”, then selected “Jit evermore 2!”. The model recovered operational context from persistent GitHub artifacts without asking the human to restate the project.

## Observed sequence
1. The model identified the Sanctum repository and retrieved its live README from `bonoj/Sanctum`.
2. The README established the reading order: `CONJOINER.md`, `CONTRACT.md`, then the selected workspace handoff. The model read both orientation documents.
3. The human named JIT Evermore II, which was not among Sanctum's explicitly enumerated workspace entrypoints. The model correctly treated the selection as authoritative rather than forcing Sieve, Abyss, or Hermeticon.
4. The model located `bonoj/bonoj.github.io/jit/evermore-2/` on `master`, listed its files, and read the full README.
5. The README supplied the game identity, implemented systems, invariants, known verification limits, retired instrumentation/testing, and current creative frontier: an open Tier III ☀️ versus 🔥 war driven by material conversion and emergent ecology.
6. The model fetched `index.html` and recorded its blob SHA `b1da3919809927e74ef91e0e5170be470093bb2e`; it inspected only a few keyword counts, not the complete behavior of the source.
7. The model reported orientation and explicitly made no changes. It did not claim a successful browser execution, deployed SHA match, or physical-device test.

## What worked
- Two short human utterances were enough to cross from a stateless conversation into a specific active project.
- Sanctum provided identity, relationship, operating protections, and navigation; Evermore's own README provided local truth. The distinction prevented a generic global handoff from overriding project-specific state.
- Direct file fetches avoided repository-search false negatives and recovered the correct independent repository path.
- The Evermore handoff was unusually effective: it preserved the *open* nature of the war frontier instead of prematurely inventing its specification; it also made deferred save/restore and retired CI explicit.
- No new UI, code, or repository scaffolding was introduced during orientation.

## Friction and failure modes
- The first GitHub-tool discovery query searched for the wrong function names and returned no matches; a second discovery found the supported fetch operations. Tool discovery remains a small avoidable cold-boot tax.
- The model spoke before it had read Sanctum, claiming a protocol it had not yet verified in this session. That assertion happened to match the repository, but should have been framed as provisional until read.
- Sanctum's workspace list did not include Evermore II. The human had to supply the destination. This is acceptable when the human chooses the world; a global index need not catalog every JIT.
- The model used keyword counts from the source as a lightweight presence check, not a semantic code audit. It should not imply otherwise.
- Reading the README is enough for conversational reorientation, not enough to safely implement a new mechanic. Implementation requires inspection of the relevant actual systems and tests where available.
- Source blob identity is not executable build identity. The browser, GitHub Pages deployment, and physical-device behavior remained unverified.

## Interpretation
Cold boot is not a restoration of hidden model memory. It is *reconstruction of working context from explicit external state*, with the human choosing the destination and the model recovering its contracts and evidence. A successful boot produces an accurate, bounded understanding of where work stopped, which facts are observed, and what remains undecided.

The architecture has three useful layers:
1. **Sanctum:** who is collaborating, why, and which operating rules protect the work.
2. **Project README/handoff:** where the authoritative state lives, what is stable, and the next open frontier.
3. **Source and runtime evidence:** what has actually been implemented, deployed, and observed.

The key efficiency gain is semantic compression: “Sanctum!” and “Jit evermore 2!” expanded into a concrete project, operational constraints, and a frontier without the human reconstructing days of work.

## Proposed refinement
- Keep Sanctum compact and stable. Do not turn it into an exhaustive world registry.
- Make each project's README the canonical cold-boot handoff, with a clear entrypoint, invariants, current frontier, and verification distinctions.
- For conversational orientation, read the README and only enough source to establish baseline. For implementation, follow source dependencies and verify behavior.
- Distinguish **located**, **read**, **understood provisionally**, **source inspected**, **committed**, **deployed**, and **runtime verified**.
- Avoid premature “ready to build” claims or inventing implementation details for intentionally open frontiers.
- Evaluate future boots by human steering required, retrieval accuracy, unnecessary operations, and continuity of creative momentum—not by tool-call count alone.

## Outcome
**Successful conversational cold boot; implementation readiness not yet established.** The human was able to return immediately to Evermore II's active creative frontier. No project source was mutated in this experiment.

# Follow-on observation — Fire colony ecological pivot (later 18 October 2026)

The cold-boot experiment above remains an independent observation: it ended with conversational orientation and no source mutation. The following happened **later** during actual Evermore II development. These phases must not be conflated.

## Why this episode matters

The human and model initially sought a ☀️–🔥 Tier III war. The first productive move was to implement only Fire: 🗿 Idols field 🦂 scorpions that acquire stone armor through real predation, and reproduce by metamorphosis. The first implementation's any-three-meals rule caused very rapid colony growth. The human pivoted to a *constrained food web*, not a spawn cap or artificial timer.

## Human-selected mechanics

- One 🍄 mushroom, one 🦴 bone, one living 🪱 worm, **one of each in any order**, produces one visible stone per ingredient: **three rocks = three stone total**.
- At fewer than three rocks, hunt only missing ingredients; if unavailable, wander toward nearest living Idol.
- At three rocks, hunt and consume one living 🐀 rat; credit one rat to Tiffany's inventory and metamorphose **in place** into an Idol. Without rat, return toward an Idol; no metamorphosis.
- Enemy contact stings and sheds a stone, reopening that stone's ingredient requirement; at zero armor the scorpion can die. Parent Idol replenishes its scorpion; the new Idol fields its own.
- No automatic conversion of loose stone into Tiffany's inventory. Existing crab work and other creatures remain independent.

## The hiccup

The model initially invented **three stone per rock**, making a full back worth nine, and the human caught it. The correct amount is **one per rock, three total**. Documentation briefly retained the obsolete any-three-meals behavior; the human required the canonical rule to be written and instrumented. The correction is an example of why cold boot must recover actual human-selected invariants rather than model extrapolations.

## Empirical evidence — executing build 86ebc0c9

The human's natural-play World Observer v1 export captured **266 game seconds** with **zero reported errors**. Counters: **106 ingredient meals = 38 mushroom + 23 bone + 45 worm**; **22 rats consumed = 22 metamorphoses**; **23 Idol births**, **eight Idol destructions**, **41 scorpion spawns**, **eight stings** and **eight armor losses**. Rat inventory rose from **99 to 121**, consistent with 22 rat credits. The eagle independently captured/delivered **28 worms**, and the octopus converted **21 mushrooms**.

At the end: **15 Idols and 19 scorpions**; **15 of 19** carried two stones, had completed mushroom and worm, and were waiting for **bones**. The bone bottleneck emerged naturally. Idol count was not monotonic: six at 150 s, three at 160 s, fifteen at 210 s, thirteen at 230 s, fifteen at 265 s. Aggregate events support the new gate and inventory accounting in this run but do not prove all per-transition behavior. Scorpion count exceeding Idol count is an observation worth inspecting, not by itself proof of a defect.

## Analysis

The change replaces unrestricted exponential growth with *resource-mediated reproduction*. Fire now depends on three ecological supply channels plus a living-rat gate. Eagles compete for worms; scavenging and remains production determine bone access; enemies can strip armor and destroy Idols. The surprising result is a colony of two-rock scorpions waiting for bones, a legible consequence of interactions among existing systems rather than scripted difficulty. The human called the result “absolutely fantastic.”

## Next human-selected frontier: ☀️ hunting 🦂

The next direction is for **☀️ Tier III to hunt rock-bearing 🔥 scorpions**, beginning the proposed tower conflict through physical stone predation. **Not yet designed or implemented.** Before editing, inspect the Evermore II README and source for Plains/Tier III, scorpion combat, loose stone, claims, worker FSM, delivery and observer instrumentation. Do not invent hunter identity, combat values, loot yield or UI. Distinguish a stone knocked loose from one physically recovered and one credited to Tiffany. Preserve existing professions, the three-distinct-meal contract and the rat metamorphosis gate. Implement only after the human selects concrete behavior; then regression-test and compare source, published build and executing device.
