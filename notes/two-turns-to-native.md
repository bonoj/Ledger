# Two Turns to Native: A Small Experiment in Model-Directed Software

**October 26, 2026 · Ledger note · retrospective, not specification**

## The observation

A human and a language model built an experimental contract-based UI workbench for the web in one conversational work turn. In a second work turn, they built an Android project and a cloud APK build pipeline representing the same small experience. One corrective turn repaired a CI environment failure. The human then installed the resulting APK on a physical Android phone and exercised it in portrait and landscape.

The remarkable feature was not the screen's sophistication. It was the **amount of standard software engineering that ceased to require the human's direct attention**.

This account deliberately omits personal names, employer names, recruiter details, interview logistics, and product branding beyond the technologies necessary to understand the experiment. It is not a claim about anyone else's internal systems.

## The sequence

### 1. A web design workbench in one turn

The starting request was to explore a small, model-directed, contract-based design system. The model created and deployed a browser workbench organized around a declarative JSON contract:

- Design tokens: colors, spacing, radius.
- Screen identity: title and subtitle.
- Component vocabulary: hero, chips, card, button.
- A live web renderer with interactive chip selection and save state.
- Inspectable Compose and XML output generators.
- Documentation and a deployment location.

The web experience was interactive. The Compose and XML tabs were **illustrative output**, not compiled Android artifacts. The JSON editor was a laboratory instrument; the human did not need to manually author the screen.

The experiment asked whether human design intent could be expressed once and rendered through different implementation idioms. The contract was an initial boundary, not a finished portable UI language.

### 2. A native Android project in a second turn

A later conversational instruction asked to cross from a chat-directed design to a functioning Android prototype.

The model created a native Android project containing:

- A Kotlin `ComponentActivity` using `setContent`.
- A Jetpack Compose screen implementing the same conceptual titles, chips, card, and actions.
- Compose Material 3 styling and explicit state.
- `rememberSaveable` for selection, save state, and an interaction counter.
- Gradle/Android plugin/Kotlin/Compose dependencies.
- An Android manifest.
- A GitHub Actions workflow to build and upload a debug APK.

The Android implementation was **hand-authored by the model from the shared design**, not mechanically generated by parsing the JSON contract. This distinction matters: the experiment proved model-mediated translation of intent, not yet a verified automatic contract compiler.

### 3. One failure, one corrective turn

The first CI run failed *before Kotlin compilation*. Its Android SDK setup action attempted to install the obsolete SDK package `tools`; the log reported `Failed to find package 'tools'` and `sdkmanager` exited with code 1.

The human surfaced the red build and a screenshot of the actual job log. The model identified the environment failure, replaced the setup step with explicit installation of modern Android SDK packages from the runner's available SDK tooling, and pushed a workflow-only fix.

The next run was reported **green**. No speculative changes to application code were needed to resolve this failure.

This is part of the experiment, not a blemish to edit away: a build pipeline failed, runtime evidence was inspected, and the correction stayed within the failing subsystem.

### 4. Native execution on a physical phone

The human downloaded and installed the debug APK and returned screenshots of the running application:

- The app rendered as a native Android UI in portrait.
- A landscape screenshot showed a wider layout.
- The card action had visibly changed from **Save idea** to **✓ Saved**.

These screenshots demonstrate installation, launch, native rendering, orientation-dependent layout, and at least one successful state transition. They do **not**, by themselves, verify every button, persistence across process death, accessibility, performance, or broad device compatibility.

The workflow required no local Android Studio or local SDK setup for the human. The model authored the project and CI configuration; cloud tooling compiled the APK; the human evaluated the actual experience.

## What became invisible

The human did not directly operate Gradle, write Kotlin, configure an Android manifest, manage Compose dependencies, or repair the SDK command line. These tasks still happened; they were simply handled beneath the conversational interface.

This is the critical distinction:

> Implementation complexity was not abolished. Much of it was absorbed into model-operated, already-existing engineering machinery.

The human's work shifted toward intent, direction, observation, and deciding what to try next. When the build failed, the human provided evidence rather than taking over the tooling.

## What was proved—and what was not

**Observed:**
- A small contract-oriented interactive web workbench could be created and deployed through conversation.
- A corresponding native Compose app and CI build configuration could be authored in another turn.
- A real CI failure could be diagnosed from logs and repaired in a corrective turn.
- The resulting APK could be installed and run on a physical Android phone.
- Native interaction state and layout could be observed in screenshots.

**Not established:**
- Automatic JSON-contract-to-Kotlin generation, compilation, and fidelity checking.
- A general-purpose, production-grade design system.
- Exact parity between web and native implementations.
- Reliable handling of networking, navigation, storage, permissions, accessibility, security, or complex application lifecycles.
- Quantified labor savings against a controlled baseline.
- Fully autonomous delivery: the human supplied direction, CI evidence, installation, and runtime feedback.

The meaningful unit of measurement here is **human attention**, not merely elapsed time or lines of code. The observation is qualitative, but concrete.

## Why the result matters

Conventional Android development already has powerful compositional primitives, build tooling, and deployment automation. A capable model can operate much of that machinery without forcing the human to attend to every technical seam.

For standard application prototypes, the limiting factor may move away from typing implementation code and toward:

1. **Design intent and experience quality** — what should happen, and how should it feel?
2. **Approved vocabulary** — which components, tokens, patterns, and constraints should implementations respect?
3. **Executable evidence** — does the real application behave correctly, not just look plausible?
4. **Iteration and recovery** — can failures be observed, isolated, corrected, and verified without imposing large coordination costs?
5. **Access** — can someone who is not operating an IDE still direct and evaluate native software?

This suggests an important inversion. Rather than asking how to help a designer produce more Kotlin, ask how much Kotlin the designer should ever need to see.

## The pre-existing machinery mattered

This was not a greenfield demonstration of a model spontaneously inventing an entire delivery organization. The collaborators already had established operational conventions:

- **Sanctum:** preserve creative momentum, constrain changes, absorb routine failures, distinguish written, built, deployed, and observed results.
- **Gate:** use the existing JIT publication route, isolate experiments, read back changes, and verify public artifacts rather than equating commits with deployments.
- **JIT/GitHub Pages:** a known experiment shelf and hosting path, requiring no new web distribution infrastructure.
- **GitHub Actions and Android tooling:** mature third-party machinery for installing dependencies, compiling, packaging, and exposing an APK artifact.

These were different forms of reuse: *organizational rules*, *deployment infrastructure*, and *implementation assets*. The experiment strongly exercised the first two. It did **not** establish reusable contract-to-native compilation or a general native component system. There is no measured count of how often the model consulted Sanctum or Gate during the original turns, so the precise causal contribution of reading those documents should not be overstated.

The practical achievement was that the human did not need to coordinate the boundaries manually. The established machinery provided a route, and the model operated within it. The one SDK failure was corrected at the failing boundary, not by rebuilding the system.

**Preserved recovery path:** the working Android build recipe, pinned toolchain, SDK fix, APK artifact steps, and physical-device verification procedure now live in [JIT Gestalt's README](https://github.com/bonoj/bonoj.github.io/blob/master/jit/gestalt/README.md), with the executable [GitHub Actions workflow](https://github.com/bonoj/bonoj.github.io/blob/master/.github/workflows/jit-gestalt-android.yml) as the authoritative implementation. The SDK fix replaced an action that attempted to install obsolete `tools` with direct installation of platform 35 and build-tools 35.0.0. No new orchestration framework was needed.

## Native as destination, not default architecture

The native Compose build was useful because the experiment explicitly asked whether conversational intent could reach an actual native application. That does not imply every future JIT world should be reimplemented in native UI code.

For a web-first executable world, a thin Android WebView shell could preserve one authoritative HTML/JavaScript/WebGL experience while adding an installable package and selective platform integration. That route is **a proposal, not a demonstrated result**. WebView compatibility, performance, permissions, storage, media, and lifecycle behavior would require device evidence.

The relevant architectural choice is therefore conditional: **build native when native interaction is the question; package the existing web experience when the question is simply getting a world onto a phone.** Neither choice changes what tonight proved.

## The next experiment

The current web contract and native app share *intent*, but the Android app is still a separately authored mirror. The next falsifiable milestone is:

**Change the contract in conversation → generate Android implementation from that contract → build APK → run it → compare observed native behavior to the web experience.**

A second, substantially different screen would test whether the machinery is composable or merely fitted to one toy.

Later work could add device-test evidence, semantic UI hierarchy capture, accessibility assertions, screenshot comparison, build provenance, and failure reporting. None of those should be claimed before they exist.

## Closing

The prototype was simple. The process was not trivial. Yet the human's participation remained remarkably light: direct an experience, surface one failed build log, install the APK, touch the result, and observe.

The lesson is not that Android engineering has become unnecessary. It is that a growing portion of **routine Android engineering can become infrastructure beneath conversation**.

The scarce attention can then return to the experience itself.
